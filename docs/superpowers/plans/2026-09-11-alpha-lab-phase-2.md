# Alpha Lab — фаза 2: масштаб

> **Для агентов:** используйте `superpowers:subagent-driven-development`. Шаги размечены чекбоксами.

**Цель:** дать возможность проверять **тысячи гипотез** и видеть результат в виде воронки отбора, а не стопки отчётов.

**Основание:** spec раздел 11, фаза 2. Замеры на реальных данных (BTCUSDT, 1h, 2022–2025, 35 064 бара) показали, что производительность **не** является ограничением.

## Что показали замеры — и почему план именно такой

| Стадия | Время | Вывод |
|---|---|---|
| Загрузка + ресемпл | 22.2 с | один раз на (символ, таймфрейм) — переиспользуется |
| `generate` + `run_backtest` | 47.6 мс | 73% внутри — Python-циклы slippage/funding |
| `validate` целиком | 662 мс | **97% из них — permutation-тест (646 мс)** |
| 10 000 конфигов, полный вердикт | **110 мин** | требование «тысячи за ночь» уже выполнено |

Отсюда: оптимизировать движок не нужно. Нужно убрать **ручную работу** — сейчас 10 000 гипотез требуют 10 000 YAML-файлов и 10 000 отчётов, которые некому прочитать.

## Пакеты работ

| # | Пакет | Что даёт |
|---|---|---|
| **P1** | Сетка гипотез | YAML-описание сетки → детерминированный список конфигураций. Без ручных файлов |
| **P2** | Пакетный прогон | Сетка × символы × таймфреймы; бары грузятся один раз на (символ, таймфрейм); результаты в хранилище; прогресс и возобновляемость |
| **P3** | Хранилище результатов | Таблица всех прогонов (DuckDB/Parquet) с запросами: отбор, сортировка, группировка |
| **P4** | Воронка отбора | Главный артефакт: из N конфигураций сколько проходит каждый гейт и **что выжило** |
| **P5** | Режим просеивания | Меньше перестановок на черновом прогоне, полный вердикт — финалистам. Документировать потерю точности |

## Глобальные ограничения

- Python через `uv`; системный Python не трогать.
- pandas/numpy; без polars. pandas 3.0.5 — `freq="1m"` = конец месяца, использовать `"1min"`.
- Комментарии и docstring — на русском, идентификаторы английские.
- TDD. Полный набор под `-W error` остаётся зелёным (369 тестов, ~53 с).
- **Одиночный прогон BTCUSDT `mr_base` 1h 2022–2025 остаётся `МЕРТВА` со всеми метриками без изменений.** Это якорь: фаза 2 добавляет инструменты, а не меняет вердикт.
- Никаких сетевых обращений в тестах.

- [x] Формат: базовый эксперимент + перебираемые оси. Оси: `params` (списки значений), `timeframes`, `symbols`.
- [x] Развёртка в список конфигураций с **детерминированным** идентификатором (порядок ключей не влияет, повторный запуск даёт тот же id).
- [x] Отвергать пустую сетку, дубликаты осей, значения не из пространства параметров стратегии.
- [x] **Предупреждать о размере**: сетка на 200 000 конфигураций должна сказать об этом до запуска, а не после.
- [x] Тест: `k ∈ {1.5, 2.0} × timeframes ∈ {1h, 4h} × symbols ∈ {BTC, ETH}` → 8 конфигураций, id стабильны.

## P2 — Пакетный прогон

**Файлы:** `src/alpha_lab/batch.py` (новый), `cli.py` (команда), `tests/`

- [x] Команда `alpha-lab sweep --grid configs/grids/mr.yaml --out results/` — прогоняет сетку.
- [x] **Бары загружаются один раз на (символ, таймфрейм)** и переиспользуются всеми конфигурациями. Сейчас 22 с на загрузку — при 10 000 конфигураций это недопустимо повторять.
- [x] **Прогресс и возобновляемость**: прогон на часы должен уметь продолжиться после падения, не повторяя сделанное. Ключ возобновления — id конфигурации в хранилище.
- [x] **Ограничение параллелизма**: движок использует numba и numpy; запускать процессы или потоки — решить по замеру, а не по интуиции. Если выигрыша нет, делать последовательно и сказать это.
- [x] Прогон не падает на одной плохой конфигурации: ошибка записывается как результат этой конфигурации, остальные продолжаются.

## P3 — Хранилище результатов

**Файлы:** `src/alpha_lab/results.py` (новый), `tests/`

- [ ] Таблица (Parquet + DuckDB) со строкой на прогон: id конфигурации, символ, таймфрейм, параметры, метрики вердикта (DSR, p-value, PBO, Sharpe, сделки, просадка, издержки), `alive`, причины, предупреждения.
- [ ] Схема **версионирована** так же, как отчёт: несовместимая версия отвергается громко, а не читается молча.
- [ ] Запросы: отбор по символу/таймфрейму/статусу, сортировка по метрике, группировка.
- [ ] **Идемпотентность**: повторная запись того же id перезаписывает строку, а не дублирует.

## P4 — Воронка отбора

**Файлы:** `src/alpha_lab/funnel.py` (новый), `cli.py` (команда `report`), `tests/`

Главный артефакт фазы. Отвечает на вопрос «нашли ли мы что-нибудь» одним экраном:

- [ ] **Воронка**: N конфигураций → прошло по числу сделок → прошло DSR → прошло p-value → прошло PBO → `alive`. С абсолютными числами и долями.
- [ ] **Разрез по таймфреймам**: на каких горизонтах выживших больше — и есть ли там вообще выжившие.
- [ ] **Разрез по символам**: то же по парам.
- [ ] **Топ выживших** с их метриками — и **явное предупреждение**, что победитель, выбранный из N по метрике, обязан проходить поправку на N попыток (DSR это уже делает, но читатель должен видеть N).
- [ ] **Честность важнее красоты**: если выживших ноль, воронка должна говорить «ноль» и не пытаться показать «лучших из мёртвых» как результат. Лучший из N мёртвых — всё ещё мёртвый.
- [ ] Экспорт в `report.js` для дашборда (та же схема-контракт).

## P5 — Режим просеивания

**Файлы:** `significance.py` или `validator.py`, `cli.py`, `tests/`

- [ ] Флаг чернового прогона: меньше перестановок (например 200 вместо 1000) → 10 000 конфигураций за ~21 мин вместо 110.
- [ ] **Документировать потерю**: с 200 перестановками минимальный достижимый p-value = 1/201 ≈ 0.005, что всё ещё ниже порога 0.05, но грубее. Записать это в результат, чтобы отчёт не смешивал точные и черновые прогоны.
- [ ] **Полный вердикт — финалистам.** Черновой прогон отбирает кандидатов, но `alive` по черновому вердикту не выносится: он может только отсеять.

## Критерии готовности фазы 2

1. Сетка из YAML разворачивается в конфигурации детерминированно, с предупреждением о размере.
2. `sweep` прогоняет сетку, переиспользуя загруженные бары, и переживает падение без потери сделанного.
3. Результаты всех прогонов лежат в запрашиваемом хранилище с версионированной схемой.
4. Воронка показывает, сколько конфигураций прошло каждый гейт, с разрезом по таймфреймам и символам.
5. Черновой режим ускоряет прогон и **явно помечает** свои результаты как грубые.
6. Реальный прогон: сетка по 4+ символам и 3+ таймфреймам выполнена, воронка построена, числа приведены.
7. Одиночный прогон BTCUSDT остаётся `МЕРТВА` с неизменными метриками.
8. Полный набор тестов зелёный под `-W error`.
