## 1. Контекст

В папке проекта лежит `index.html` (2551 строка) — лендинг для индикатора «Mean Reversion Quant Pro» на Pine Script v6. Внутри: описание модели (z-score, процесс Орнштейна–Уленбека, полужизнь, ATR-риск), два скрипта Pine, синтетическая демонстрация и Монте-Карло «бэктест».

**Ключевое ограничение текущего артефакта:** функция `runTrades()` (строка 2448) генерирует цену как `price = prev + θ(μ − prev) + σ·ε`, то есть проверяет стратегию на данных, порождённых той же моделью, которую стратегия эксплуатирует. Результат такого теста гарантирован математикой и ничего не говорит о рынке. Реальных рыночных данных в проекте нет.

**Цель проекта Alpha Lab:** построить исследовательский полигон, который позволяет проверять торговые гипотезы на реальных данных и — главное — **честно отбраковывать** те, что являются подгонкой под историю.

### Принятые решения

| Вопрос | Решение |
|---|---|
| Назначение | Реальная торговля своими деньгами |
| Рынок | Криптовалюты (Binance USDT-margined perpetual futures) |
| Горизонт | Движок агностичен: от минутных до дневных баров |
| Точка старта | Ядро + слой валидации (фазы 0–1) |
| Юниверс | Фокусированный: 20–30 ликвидных перпетуалов |
| Первый подопытный | Существующая MR-стратегия из `index.html`, перенесённая в Python |
| Визуализация | Дашборд нужен с фазы 0, не откладывается |

### Принцип, определяющий всю архитектуру

Полигон тратит большую часть усилий не на генерацию идей, а на различение закономерности и совпадения. В исторических данных можно подобрать что угодно; ценность представляет только умение отличить реальный edge от случайного. Поэтому слой валидации проектируется первым и делается «слепым» — он не знает о стратегии ничего, кроме её результатов.

## 4. Компоненты и интерфейсы

### 4.1 Strategy

```python
class Strategy(Protocol):
    name: str

    def generate(self, bars: pd.DataFrame) -> pd.Series:
        """Целевая позиция: -1.0 (полный шорт) … 0.0 … +1.0 (полный лонг).

        bars: колонки ts, open, high, low, close, volume, sorted by ts.
        Обязан использовать только информацию до момента t включительно.
        Проверяется автотестом look-ahead (см. 8.1).
        """
```

Интерфейс намеренно узкий: одна функция. Всё, что сложнее, — это уже композиция стратегий, а не новая абстракция.

### 4.2 CostModel

Итоговый интерфейс (план, Task 8; `engine/costs.py`):

```python
class CostModel(Protocol):
    def fee_bps(self) -> float: ...
    def slippage_bps(self, order_notional: float, bar_quote_volume: float) -> float: ...
    def funding_cost(self, position: float, rate: float) -> float: ...
```

Первоначальная редакция описывала интерфейс с `fee(symbol, ts, notional, maker)`, `slippage(bar, order_size)`, `funding(symbol, ts, notional)` и `borrow(...)` — он был заменён при планировании: ставки funding берутся из исторического ряда, выровненного по барам (`data/query.align_funding_to_bars`), а не запрашиваются у модели; `borrow` для USDT-перпетуалов не моделируется (его роль играет funding).

`slippage_bps` принимает размер заявки и котируемый объём **того бара, на котором исполняется заявка**, и является нелинейной функцией их отношения. Это принципиально: модель «проскальзывание = 1 тик» не различает $100 и $100k и делает невидимой зависимость результата от капитала.

`funding_cost` начисляется на удерживаемую позицию в каждом баре, где есть ненулевая историческая ставка (биржевой интервал — обычно 8 часов: 00:00, 08:00, 16:00 UTC). Без funding бэктест систематически завышает результат для всех стратегий, держащих позицию дольше нескольких часов. Если ряд ставок недоступен или пуст, CLI обязан предупредить, что издержки занижены (через `warnings` вердикта и отдельную строку в stderr), а не показывать funding = 0 как факт.

**Реализации:**
- `ZeroCost` — для инвариантных тестов.
- `RealisticCost` — тейкер/мейкер по фактическим тарифам Binance (VIP0), проскальзывание от доли объёма бара, реальные исторические ставки funding.

### 4.3 Validator

```python
@dataclass(frozen=True)
class Verdict:
    strategy_name: str
    sharpe: float
    dsr: float              # Deflated Sharpe Ratio
    pbo: float              # Probability of Backtest Overfitting
    p_value: float          # permutation-тест
    max_dd: float
    total_return: float
    trades: int
    n_configs_tried: int    # для поправки на множественные сравнения
    alive: bool
    reasons: tuple[str, ...]
    warnings: tuple[str, ...]  # гейты, НЕ проверенные в этом прогоне; на alive не влияют
    experiment_id: str      # хэш(конфиг + версия данных + git hash)
```

Вердикт бинарный — `alive: true/false` — плюс человекочитаемые причины. Формулировка «Sharpe 1.8, вроде неплохо» не допускается: она оставляет пространство для самообмана.

`reasons` и `warnings` — разные каналы. `reasons` объясняют, почему стратегия мертва; `warnings` фиксируют гейты, которые в данном прогоне не запускались (одиночная конфигурация без матрицы для PBO, отсутствие funding, разрывы данных). Непроверенный гейт не делает стратегию мёртвой — отсутствие входных данных не дефект стратегии, — но и не считается пройденным: отчёт, CLI и дашборд обязаны показать предупреждения явно.

## 6. Слой валидации

Четыре механизма, каждый закрывает конкретный способ обмануть себя.

### 6.1 Purged K-Fold с embargo

**Проблема:** признаки считаются на скользящем окне (например, 20 баров). Train и test пересекаются по времени, и модель видит будущее через перекрытие окон. `train_test_split` этого не обнаруживает.

**Решение:** purge — из train удаляются все наблюдения, чьё окно признаков заглядывает в test; embargo — добавляется зазор после test-блока (признаки инерционны).

Реализация: `validation/splits.py`, параметры `n_splits`, `purge_window`, `embargo`.

### 6.2 Deflated Sharpe Ratio (DSR)

**Проблема:** при переборе N конфигураций выбранный по максимуму Sharpe почти наверняка завышен. Ожидаемый максимум Sharpe у N случайных стратегий растёт как `√(2·ln N)`; при N=500 это ≈ 3.5.

**Решение:** поправка Бейли и Лопеса де Прадо. Сырой Sharpe дефлируется на число испытаний, длину ряда, асимметрию и эксцесс распределения доходностей.

`n_configs_tried` берётся из журнала экспериментов, а не задаётся вручную.

### 6.3 Probability of Backtest Overfitting (PBO)

**Проблема:** «повезло на истории».

**Решение:** разбиение истории на блоки; проверка, как часто конфигурация, лучшая на одной половине, оказывается в худшей половине на другой. Высокое PBO означает подгонку.

### 6.4 Permutation-тест

**Проблема:** «а может, оно само так вышло».

**Решение:** перемешивание **позиций** относительно доходностей цены; пересчёт доходности стратегии на каждой перемешанной версии; построение распределения Sharpe под нулевой гипотезой; честный p-value.

Нулевая гипотеза формулируется как «сигнал не связан с доходностями». Перемешивать сами доходности нельзя: Sharpe = mean/std инвариантен к перестановке, поэтому такой тест дал бы p-value ≡ 1.0 и не отклонял бы ничего. Ломать нужно именно соответствие «сигнал ↔ доходность».

### 6.5 Пороги вердикта

Стратегия признаётся `alive` только при одновременном выполнении:
- `dsr > 0.95` — фактический порог кода (`min_dsr` в `validator.py`; первоначальная редакция говорила `dsr > 0`). DSR — это вероятность того, что истинный Sharpe больше нуля, и требование 0.95 означает 95%-ю уверенность, а не просто положительный знак оценки: порог намеренно консервативен и отсекает края, у которых «плюс» держится на нескольких наблюдениях.
- `pbo < 0.5` — **гейт фазы 2**. PBO считается по матрице доходностей многих конфигураций (T × N); одиночный прогон CLI такую матрицу не порождает. Когда матрицы нет, PBO не вычисляется, условие остаётся непроверенным, и вердикт сообщает об этом через канал `warnings` (не через `reasons`: отсутствие матрицы — свойство прогона, а не дефект стратегии). Когда матрица передана, но непригодна для CSCV (меньше 2 конфигураций или меньше 2·n_blocks наблюдений), вердикт, как и раньше, мёртв с явной причиной.
- `p_value < 0.05`
- `trades >= 100` (иначе статистики недостаточно)

Пороги задаются в конфиге, значения по умолчанию фиксируются в коде. При `trades < 100` вердикт — `alive: false` с причиной «недостаточно сделок», а не «не проверено».

**Визуальный язык:** переиспользуется эстетика `index.html` — тёмный фон `#0b0e14`, акценты amber/sky/emerald, шрифты Inter + JetBrains Mono, Tailwind через CDN. Это не самоцель: единый вид проекта и лендинга.

**Содержимое (фаза 0–1):**
1. **Панель вердикта** — `alive`/`dead`, DSR, PBO, p-value, Sharpe, max DD, число сделок. Главный элемент экрана.

3. **Цена с сигналами** — бары, входы/выходы, полосы z-score.
4. **Распределение сделок** — гистограмма R-мультипликаторов.

## 8. Защита от самообмана

Это не обработка исключений, а встроенные гейты против когнитивных ошибок.

### 8.1 Почему look-ahead нельзя поймать статистикой

Первоначальная редакция этого раздела требовала, чтобы валидатор «убивал» стратегию, торгующую по будущему бару. **Требование невыполнимо, и это доказано экспериментально** (Task 17): подглядывающая стратегия получает `alive=True` с DSR 1.0 и p-value 0.001.

Причина фундаментальна. Валидатор видит только реализованную выборку — `returns`, `price_returns`, `positions`. Две гипотезы:

- **(A)** позиция `h_t` посчитана по информации до `t` и коррелирует с доходностью `r_t`;
- **(B)** позиция `h_t` посчитана из самого `r_t`.

...порождают **одинаковое совместное распределение** `(r_t, h_t)`. Никакая статистика по этой выборке их не различит: различие лежит в отображении «вход → позиция», а не в распределении выхода. Более того, любое дополнительное допущение (например, об эффективности рынка), которое позволило бы их различить, отвергало бы и настоящий edge.

Ни один из четырёх механизмов не помогает: purged CV не участвует в вердикте и не помог бы (утечка внутри строки); DSR и PBO измеряют смещение отбора по числу попыток; permutation-тест корректно разрушает связь «сигнал ↔ доходность» — а у подглядывающей стратегии позиции выровнены с доходностью **по построению**, и тест не может отличить это от мастерства.

**Следствие:** диагностика ёмкости (`over_capacity`) тоже не является детектором — замерено, что при капитале 10 она поднята и вердикт всё равно `alive=True`, а при капитале 1 опущена, и стратегия «зарабатывает» 1.79e9.

**Единственная работающая защита — запрос к функции решения.** `generate(bars[:k])` обязана побитово совпадать с `generate(bars)[:k]` для набора значений `k`. Это применяется к каждой стратегии через обязательный harness (`tests/fixtures/causality.py`), а не как разовый тест одной модели.

**Точность гарантии.** Точка усечения `k` вскрывает зависимость от будущего ровно в одной позиции — последней в префиксе (`k−1`): все предыдущие позиции присутствуют и в усечённом прогоне, и в полном, поэтому утечка в них при данном `k` невидима. Отсюда политика плотности: при `n ≤ 600` точки берутся сплошь (полное покрытие всех позиций), выше — плотная сетка не реже 200 точек. **Утечка, целиком лежащая между точками разреза, на длинном ряде теоретически может остаться незамеченной** — для полной гарантии harness принимает `cut_points="all"`.

**Что остаётся незащищённым:** утечка на уровне признаков (признак, заглядывающий в `t+1` внутри окна нормализации) — harness судит по решению стратегии, а не по её входам; поведение последнего бара полного ряда (позиция `n−1` в точки усечения не входит); стратегия, ведущая себя причинно только под усечением; отсутствие harness-теста у новой стратегии. Первое закрывается причинностным тестом самих трансформов признаков, последнее — обязательностью harness в реестре стратегий (фаза 2).

**Индексная конвенция (обязательна для стратегий).** `generate` обязан вернуть `Series`, чей индекс совпадает с `bars.index`. Движок `run_backtest` потребляет позиции позиционно и проверяет только длину, поэтому стратегия с дефолтным `RangeIndex` в нём работать будет, а harness её отвергнет. Это сделано намеренно: молчаливое выравнивание по меткам скрыло бы перестановку порядка.

| Ловушка | Механизм защиты |
|---|---|
| **Look-ahead** | **Ловится проверкой причинности над стратегией, а не статистикой над результатами.** Обязательный harness-тест: `generate(bars[:k])` должна совпадать с `generate(bars)[:k]` для набора `k`. Применяется к **каждой** стратегии, а не только к MR. Статистический валидатор здесь бессилен по построению (см. 8.1). |
| **Выживаемость** | Делистингованные пары остаются в юниверсе. |
| **Грязные данные** | Бары с аномалиями/нулевым объёмом → стратегия не торгует (`clean_mask`). Интерполяция запрещена. Разрывы (пропущенные бары) в фазах 0–1 только считаются и попадают в `extra`/`warnings`; маскирование разрывов не реализовано — это осознанное решение владельца. |
| **Множественные сравнения** | Каждый прогон логируется; DSR автоматически применяет поправку по числу конфигов в журнале. |
| **Невоспроизводимость** | `experiment_id = hash(config + data_version + git_hash)`. Один ID → один результат. |
| **Тихая деградация** | Любой отброшенный бар, пропущенная пара или упавшая проверка логируется в отчёт, а не проглатывается. |

## 9. Тестирование

Три уровня, каждый ловит свой класс ошибок.

### 9.1 Синтетика с известным ответом

OU-симуляция из `index.html` используется как фикстур. Истинные θ и σ известны, следовательно известно, должна ли MR-стратегия заработать и сколько именно.

**Критерий:** если полигон на этих данных говорит «мертва» — баг в движке, а не в рынке.

### 9.2 Ловушки

Фактический набор (`tests/fixtures/traps.py` и локальные классы `test_traps.py`):
- `LookAheadStrategy` — торгует по цене следующего бара.
- `PerfectForesightStrategy` — знает весь будущий ряд.
- `OverfitNoiseStrategy` — подогнана под конкретный исторический отрезок.
- `AlwaysLongStrategy` — всегда в лонге; контроль на отсутствие альфы (причинна, harness её пропускает).
- Локальные утечки в `test_traps.py` (`_SegmentLeak`, `_WarmupLeak`, `_ParityLeak`, `_MisalignedIndexStrategy`) — проверяют плотность сетки усечений и индексную конвенцию harness, а не валидатор.

`DirtyDataStrategy` из первоначальной редакции **не построена**: отдельной стратегии-ловушки нет. Грязные бары закрывает `clean_mask` (стратегия на них не торгует) плюс предупреждение CLI; см. критерий 3 в разделе 12.

**Критерий:** статистические ловушки (шум, подгонка под отрезок, недостаток сделок, множество попыток) обязан убить `validate()`; подглядывание (`LookAheadStrategy`, `PerfectForesightStrategy`) статистикой не ловится в принципе (8.1) — его обязан поймать причинностный harness `tests/fixtures/causality.py`. Это тест валидатора и harness, а не стратегий.

### 9.3 Инварианты издержек

- Нулевые комиссии → результат совпадает с наивным бэктестом.
- Комиссия 10% → стратегия разоряется.
- Рост издержек → монотонное падение доходности.

## 12. Критерии успеха фаз 0–1

1. `uv run alpha-lab ingest --config configs/universe.yaml` скачивает и раскладывает данные в `D:\alpha-lab\data`.
2. `uv run alpha-lab validate --config configs/experiments/mr_base.yaml` выдаёт `Verdict` и `report.json`. (Стратегия берётся из конфига; отдельного флага `--strategy` у CLI нет.)
3. Ловушки из 9.2 обезврежены (автотесты зелёные). Статистические (шум, подгонка под отрезок, нехватка сделок, множество попыток) убивает `validate()` — `test_all_traps_are_killed_by_validator`. Подглядывание (`LookAheadStrategy`, `PerfectForesightStrategy`) статистикой не ловится по построению (8.1); его ловит причинностный harness (`test_causality_harness_catches_*`). Исходная формулировка «валидатор убивает все ловушки» неверна; `DirtyDataStrategy` из 9.2 не построена.
4. Контроль края, а не сквозной прогон MR. Теста, который прогоняет MR на синтетических `ou_bars` целиком через `validate()`, в фазах 0–1 нет (план отображает критерий на generic-edge контроль). Фактически утверждается: `test_strong_edge_survives_validation` — настоящий край у границы (годовой Sharpe ≈ 1.7 при пороге ≈ 1.1) остаётся `alive=True`; `test_edge_below_boundary_is_killed` — край слабее порога даёт `alive=False` за статистику, а не за отсутствие входов.
5. Дашборд открывается двойным кликом и отображает equity, просадку, вердикт и разбивку издержек.
6. Получен первый вердикт по реальной MR-стратегии — любой, включая «мертва».
7. Воспроизводимость в ослабленном виде: один и тот же `experiment_id` (хэш конфига, версии данных и git hash) при тех же входах даёт тот же вердикт. Бит-в-бит `report.json` не воспроизводится: `generated_at` — метка времени, а `n_trials` берётся из журнала попыток и растёт с каждым повторным прогоном того же конфига, поэтому DSR, а у границы и `alive`, может отличаться. Исходная формулировка невыполнима; проверяется совпадение `experiment_id`, а не побайтовое равенство отчёта.
